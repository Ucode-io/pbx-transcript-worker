# Раскатка: полировка транскриптов через Gemini

Дата: 2026-09-02. Репозиторий: `Ucode-io/pbx-transcript-worker`, ветка `main`,
коммиты `d7e1df3`, `cd3f1a0`, `567eb84` — **уже в `main`, образ собран и лежит в
ghcr**.

Осталось только то, что требует доступа к кластеру: положить ключ в секрет и
перезапустить под. Это ~3 команды, всё остальное сделано.

> **Статус на 12:40 UTC 02.09.** Полировка в проде уже отработала на звонке
> `5dc237fc-f5fe-4476-8c7b-f56e3104077b` (12:10:47) — текст пришёл с пунктуацией
> и кириллицей, до этого был сырой нижний регистр. Но очередь стоит: 8 звонков
> со статусом `answered` и записью висят нерасшифрованными, четыре из них с 20
> августа. Причина найдена и исправлена в `567eb84` — нужен рестарт пода на
> новом образе (раздел 3).

## 1. Что было сломано

Полировку (LLM-вычитку распознанного текста) смержили 25 августа, но в проде она
не сработала ни разу. Причин три, и все три были незаметны:

1. **Под ни разу не перезапускали.** Тег образа `latest`, CI собирает и пушит, но
   Deployment накатан руками — без `rollout restart` в поде остаётся старый
   бинарь. Джоб `deploy` в CI при этом красный с 14 августа (он правит
   `deployments/clusters/.../values.yaml` в ArgoCD-репозитории, а записи для
   этого сервиса там нет), так что «красный CI» перестал что-либо значить.
2. **Ключ был опциональным.** В `k8s/deployment.yaml` стоял `optional: true`, а
   код при пустом `GOOGLE_AI_API_KEY` молча пропускал шаг — без единой строки в
   логе. Внешне это неотличимо от «модель ничего не исправила».
3. **Всё или ничего.** Весь звонок уходил в модель одним JSON-массивом (звонок на
   10 минут — это 100–200 сегментов whisper). Ответ обязан был совпасть по числу
   строк, иначе таймкоды разъехались бы; модель роняла одну строку — и
   выбрасывались **все** правки звонка.

Дополнительно: с 25 августа **сборка образа вообще падала** — модель
`ggml-rubaistt.bin` тянулась с `github.com/MuhammadMirrr/uzbek-dictation`, а этот
репозиторий удалён целиком (404, не только ассет).

И ещё две проблемы, найденные уже по данным прода (исправлены в `567eb84`):

4. **`CALL_TIMEOUT_SECONDS=600` резал длинные звонки.** По факту: стерео на 262 с
   успевает, на 271 с — уже нет. Это ~1.13 с работы на секунду моно-аудио, а
   каналов два. Все стерео длиннее ~4.5 минут не расшифровывались никогда — с 20
   августа так висят четыре звонка (271, 401, 883, 981 с). Дефолт поднят до 1800 с
   (стерео примерно до 13 минут).
5. **Один медленный звонок блокировал всю очередь.** Обрыв батча по ошибке
   полировки (п. 2 выше) не отличал «API умер» от «этот звонок исчерпал свой
   таймаут», поэтому вечно падающий длинный звонок останавливал обработку всех
   остальных, цикл за циклом. Теперь батч останавливается только если причина не
   в таймауте самого звонка.

## 2. Что изменено в коде

| Файл | Изменение |
|---|---|
| `cmd/worker/config.go` | `GOOGLE_AI_API_KEY` обязателен — воркер падает на старте, если ключа нет. `GOOGLE_AI_API_KEY` и `GEMINI_MODEL` принимают **список через запятую** |
| `cmd/worker/polish.go` | В запрос кладётся **аудио звонка** (mono 16 кГц mp3 32 кбит/с) — модель правит текст по звуку, а не по догадке. Нет аудио или оно больше 12 МБ — полировка идёт по тексту, звонок не теряется |
| `cmd/worker/polish.go` | Каждая строка уходит с интервалом `from_sec`/`to_sec` и говорящим. Без этого модель, услышав микс, перекладывает речь между строками — на тесте реплика оператора попала в строку клиента. С привязкой строка правится только по своему куску записи |
| `cmd/worker/polish.go` | Ротация по парам «ключ × модель»: 429 или битый ключ стоит одного запроса, дальше берётся следующая пара |
| `cmd/worker/transcribe.go` | Перед полировкой звонок микшируется в `mix.mp3` одним вызовом ffmpeg (best-effort) |
| `cmd/worker/polish.go` | Чанки по 40 строк; каналы сливаются в хронологический диалог (модель видит контекст соседних реплик); чанк с неверным числом строк делится пополам вплоть до одной строки; лог на каждый исход |
| `cmd/worker/transcribe.go` | Незаполированный звонок **не сохраняется** — остаётся в очереди и повторяется на следующем цикле |
| `cmd/worker/main.go` | Ошибка полировки прерывает батч, чтобы не жечь whisper на 5 звонках подряд при недоступном API |
| `k8s/deployment.yaml` | `optional: true` у секрета убран |
| `Dockerfile` | Модель копируется из нашего же образа по digest вместо удалённого репозитория |

Смысл: полировка теперь обязательная часть транскрипта, а не «best effort». Либо
в колонке лежит вычищенный текст, либо не лежит ничего и звонок в очереди.

Проверено живым вызовом API: звонок на два канала, 50 строк, два чанка — 50 из 50
строк исправлены, таймкоды не тронуты. `si-ar-em → CRM`, `mpc → MCP`,
`visper → Whisper`, `privet ya hotel uznat → Привет, я хотел узнать`,
`u nas odin es → У нас 1С` (последнее — уже из контекста соседних реплик).

## 3. Что нужно сделать (раскатка)

Нужен доступ к `ucode-prod` и ключ Google AI Studio — **ключ пришлют отдельно, в
этом файле его нет**.

```sh
export KUBECONFIG=~/.kube/ucode.conf     # свой путь
K="kubectl -n ucode-prod"

# 1. ключ в секрет (без него под теперь не стартует — это сделано намеренно)
$K patch secret pbx-transcript-worker-config --type merge \
  -p '{"stringData":{"GOOGLE_AI_API_KEY":"<КЛЮЧ1>,<КЛЮЧ2>,<КЛЮЧ3>"}}'

# 2. манифест (в нём убран optional: true) + ОБЯЗАТЕЛЬНО рестарт:
#    тег latest, без рестарта под останется на старом образе
$K apply -f k8s/deployment.yaml
$K rollout restart deploy/pbx-transcript-worker
$K rollout status  deploy/pbx-transcript-worker --timeout=5m

# 3. проверка
$K logs -f deploy/pbx-transcript-worker --tail=100 | grep -E "polish|call |whisper-server"
```

Актуальный образ в ghcr: `ghcr.io/ucode-io/pbx-transcript-worker:latest` →
`sha256:5e60f414552817bf4eacc1c89168c2db55dba358dbf8bfd16af81c728c473a8e`
(коммит `24fda08`, сборка 03.09 04:06 UTC).
Сверить, что под поднялся именно на нём:

```sh
kubectl -n ucode-prod get pod -l app=pbx-transcript-worker \
  -o jsonpath='{.items[0].status.containerStatuses[0].imageID}{"\n"}'
```

## 4. Как понять, что заработало

На каждый расшифрованный звонок в логе должна быть строка:

```
polish: 137 of 140 lines rewritten
transcribed call <uuid> (stereo)
```

Разбор остальных вариантов:

| Строка в логе | Что значит | Что делать |
|---|---|---|
| `config: GOOGLE_AI_API_KEY is required` (под в CrashLoop) | ключ не доехал в секрет | повторить шаг 1, проверить `kubectl -n ucode-prod get secret pbx-transcript-worker-config -o jsonpath='{.data.GOOGLE_AI_API_KEY}' \| wc -c` |
| `polish: 0 of N lines rewritten` | API отвечает, но текст не меняется | смотреть модель (`GEMINI_MODEL`, по умолчанию `gemini-3.6-flash`) и промпт в `cmd/worker/polish.go` |
| `polish stopped ...: gemini status 429` | упёрлись в квоту бесплатного тарифа AI Studio | включить биллинг в Google AI Studio |
| `polish stopped ...: dial tcp ... i/o timeout` | из пода нет выхода на `generativelanguage.googleapis.com` | проверить egress/NetworkPolicy на `ucode-prod` — **это единственное, что не проверялось**, ключ тестировался с ноутбука, не из кластера |
| `polish stopped ...: gemini status 400/403` | плохой ключ или неизвестная модель | проверить ключ и `GEMINI_MODEL` |
| `call <uuid>: polish at line ...` без `transcribed call` | звонок намеренно не сохранён, остался в очереди | после починки причины он подхватится сам |

Квота (проверено 03.09): бесплатный тариф AI Studio даёт **20 запросов в сутки
на проект и на модель** (`GenerateRequestsPerDayPerProjectPerModel-FreeTier`,
`limit: 20, model: gemini-3.6-flash`). Отсюда список ключей: каждая пара
«ключ × модель» — отдельное ведро, три ключа из разных аккаунтов дают 60
запросов в сутки. Звонок стоит 1 запрос на каждые 40 строк (медиана по проду —
1 запрос на звонок, максимум 2), а поток — 2 звонка в день, пик 13. То есть
бесплатного лимита хватает с запасом, включая разовый перезалив старых 67
звонков (~65 запросов).

Что важно знать про сами ключи (состояние на 03.09): ключ №1 упирается в
дневной лимит free tier, ключ №2 отвечает `Your prepayment credits are
depleted` — это платный аккаунт без денег, он не чинится ожиданием, ключ №3
рабочий. Ротация это переживает (каждый мимо — один запрос), но если ключей
станет мало, дешевле включить биллинг на одном, чем заводить новые аккаунты:
при таком объёме это центы в месяц, а плодить проекты ради бесплатной квоты
Google считает обходом лимитов.

## 5. Старые звонки

Очередь воркера — это звонки с пустой колонкой `transcript`, поэтому уже
расшифрованные записи сами не переполируются. Чтобы перезалить, колонку надо
очистить — звонок вернётся в очередь и пройдёт полный цикл (whisper + полировка,
~1.29× от длительности записи, по 5 звонков за 30 секунд).

```sh
curl -X PUT 'https://api.admin.u-code.io/v2/items/pbx_calls?from-ofs=true' \
  -H 'authorization: API-KEY' -H 'X-API-KEY: <app_id ProfessionalCRM>' \
  -H 'Content-Type: application/json' \
  -d '{"data":{"guid":"<call-guid>","transcript":""},"disable_faas":true}'
```

Сначала на **одном** звонке. И проверь, по чему фильтрует `pbx_list_untranscribed`
в FaaS (`professional-crm-pbx-integration-call`): если по `IS NULL`, а не по
пустой строке, надо слать `"transcript": null`, иначе запись в очередь не
вернётся.

## 6. Почему текст был непонятным (и почему это не полировка)

Whisper не ломался: путь распознавания не менялся с 14 августа — те же флаги
`--vad -vm silero -sns -ml 90 -sow`, та же модель, тот же ffmpeg. Изменился вход.
До 17 августа записи приходили от АТС одним mp3 (8 кГц, 16 кбит/с) — **микс обеих
сторон**, и whisper видел диалог целиком. С 17 августа пишет браузер оператора
(`call-stereo-*.webm`, opus, 2 канала), и каждый канал распознаётся отдельно.

Замеры по трём записям (кадры 200 мс, порог −45 дБ): в моно-миксе речь занимает
73% записи, в стерео канал клиента активен 16–27%, между фразами −70 дБ (цифровая
тишина). Три четверти канала — пустота и шум, а это ровно то место, где whisper
галлюцинирует (`engine sound`, дубли реплик). Плюс каждый канал лишён контекста
второй стороны, а декодер опирается на предыдущий текст. Качество звука ни при
чём: обе эпохи обрезаны телефоном по 3.4 кГц, каналы разделены корректно
(корреляция огибающих отрицательная).

Полировка по тексту это не лечила — она делала непонятное аккуратным. Поэтому
теперь в запрос идёт аудио, и на том же количестве запросов получается разбор по
звуку. Проверено на проде: `engine sound. Alo. Rayon, salom, salom, alo. Kim?
Rossiya televizor.` → `Alo. Vaalaykum assalom, assalom. Kim? Adashdingiz,
og'ayni.` (клиент говорит «вы ошиблись номером»).

Если после раскатки качества всё равно не хватит, следующий шаг — распознавать
звук сразу моделью (`gemini-3.5-transcribe`), оставив whisper как бесплатный
офлайн-фолбэк и источник таймкодов.

## 7. Не баг: `00:18` на карточке при записи в 38 секунд

Поле `pbx_calls.duration` — это **время разговора от АТС**, а запись содержит ещё
и гудки. Пример (`5dc237fc-f5fe-4476-8c7b-f56e3104077b`): `started_at` 12:10:09,
строка создана в 12:10:47 (звонок 38 с), `duration = 18`, а первая речь в
транскрипте начинается на 20.9 с — то есть 21 секунда дозвона плюс 17 секунд
разговора. Транскрипт покрывает всю запись целиком (последний сегмент 37.6 с),
ничего не теряется.

Плашка в CRM показывает `metadata.duration` (`CrmCommentsTimeline.tsx:299`), а
плеер играет весь файл, отсюда расхождение. Решать на фронте: либо показывать
длину записи, либо подписать плашку как «разговор». Таймкоды транскрипта — по
таймлайну записи, то есть с плеером они совпадают.

## 8. Технический долг (не блокирует раскатку)

1. **Модель живёт только внутри образа.** `Dockerfile` берёт `ggml-rubaistt.bin`
   из `ghcr.io/ucode-io/pbx-transcript-worker@sha256:1cda8f9a…` (тег `5`, сборка
   25 августа) — это единственная уцелевшая копия ggml-конверсии: на HuggingFace
   лежат только safetensors (`islomov/rubaistt_v2_medium`). Если этот образ
   когда-нибудь вычистят из ghcr, сборка встанет намертво. Правильное решение —
   выложить файл (823 369 796 байт) в релиз этого репозитория или на CDN и
   вернуть `curl` на свой хост.
2. **Джоб `deploy` в CI всегда красный** — нет записи
   `deployments/clusters/<cluster>/<ns>/pbx-transcript-worker/values.yaml` в
   ArgoCD-репозитории. Пока сервис катается руками, это шум, но из-за него
   красный CI перестаёт быть сигналом. Либо завести запись и перейти на ArgoCD,
   либо убрать джоб из workflow.
3. **Звонки длиннее таймаута висят вечно.** Очередь — это пустая колонка
   `transcript`, поэтому звонок, который не укладывается в `CALL_TIMEOUT_SECONDS`,
   будет перезапускаться каждый цикл и жечь процессор впустую. Сейчас это четыре
   записи от 20 августа (401, 883, 981 с — стерео, им нужно ~15–40 минут). Пока
   их проще пометить руками (записать в `transcript` любую заглушку) или поднять
   таймаут разово; по-хорошему нужен признак «пропущен» в FaaS.
4. **Смешанные фразы.** Русские вставки внутри узбекского предложения модель
   переводит в кириллицу: `yaxshi men sizga kommercheskoe predlozhenie yuboraman`
   → `Yaxshi, men sizga коммерческое предложение yuboraman`. Если для поиска
   нужен единый скрипт в строке — это одна строка правил в `polishPrompt`
   (`cmd/worker/polish.go`).

## 9. Локальная проверка без кластера

Живой вызов API из тестов (ключ не хранится в репозитории):

```sh
GOOGLE_AI_API_KEY=<ключ> go test ./cmd/worker -run Live -v
```

Печатает `было -> стало` по строкам. Остальные тесты — `go test ./cmd/worker`,
сети не требуют.
